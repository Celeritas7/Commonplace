🧰 PART XII · PUTTING IT ALL TOGETHER

The Core Guidelines

There is an official answer to "what does good modern C++ look like?" — the C++ Core Guidelines, edited by Bjarne Stroustrup, who designed the language, and Herb Sutter. It runs to hundreds of rules, which is far too many to read now. Here are five that between them cover most of what goes wrong, and every one of them is something this book has already been quietly doing.

1 Why this matters

Forty years of advice, sorted out 📜

Every language accumulates folklore about how it ought to be written, and C++ — which is forty years old and has been through five major revisions — accumulated more than most. Some of that advice was excellent. A lot of it was excellent in 1998 and is now actively harmful, and it is all still on the internet, indistinguishable from the good advice.

So in 2015 Bjarne Stroustrup, who designed C++, and Herb Sutter wrote the advice down properly. The C++ Core Guidelines are a public, maintained document of a few hundred numbered rules, each with a reason and examples. They live at isocpp.github.io/CppCoreGuidelines.

Two things make them more useful than the usual list of opinions. Each rule has an ID — ES.20, R.1, F.16 — so people can point at one precisely in a code review. And most are machine-checkable: run clang-tidy over your code and it will tell you which ones you are breaking, by number.

You are not going to read hundreds of rules, and you should not try. What follows is five, chosen because they catch the most common ways a beginner's C++ goes wrong — and because you have met all five already, spread across this book, without them having names. Putting names to them is what lets you look the rest up when you need them.
2 Rules 1 and 2

Initialise everything, freeze what you can 🪫

ES.20 — Always initialize an object.

int count;              // ✗ holds whatever was in that memory
int count = 0;          // ✓ holds 0
std::string name;       // ✓ fine — a class initialises itself

An uninitialised int does not contain zero. It contains whatever bytes happened to be lying at that address, so the program behaves differently depending on what ran before it. That is the worst kind of bug: it works on your machine, fails on someone else's, and disappears when you add a cout to investigate.

You saw the compiler struggle with this in 12.5 — -Wuninitialized only fires from -O1 upward, and even then it cannot see every path. Initialising costs one character and removes the entire category.

P.10 — Prefer immutable data to mutable data.

const double taxRate = 0.08;
void print(const Task& t) const;   // doesn't change t, or *this

Lesson 2.7 introduced const as a promise the compiler enforces. The guideline says to make that your default and drop it only where you must. The gain is not safety alone — it is that a reader can tell, at a glance, which parts of a function are capable of changing anything.

3 Rules 3 and 4

How to pass, and who owns what 📦

F.16 — For "in" parameters, pass cheaply-copied types by value and others by reference to const.

This is the single most-consulted rule in the whole document, because every function you write raises the question. The answer is a two-line decision:

ParameterHow to take itWhy
int, double, char, boolby value — int ncopying is one machine word; a reference would cost more
std::string, std::vector, your classesby const ref — const T& tno copy at all, and const proves you won't change it
something you intend to modifyby ref — T& tthe caller can see, at the call site, that it may change
 
// ✗ copies the whole vector on every call
double average(std::vector<double> values);

// ✓ no copy, and const says it stays untouched
double average(const std::vector<double>& values);

The rule of thumb people carry around: if it fits in a couple of machine words, pass it by value; otherwise const&.

R.1 — Manage resources automatically using resource handles and RAII.

// ✗ leaks the moment anything throws before the delete
Task* t = new Task("buy milk");
process(t);
delete t;

// ✓ destroyed automatically, on every path out
auto t = std::make_unique<Task>("buy milk");   // (C++14)
process(*t);

This is the idea Part VIII was built around, stated as a rule: every resource — memory, a file handle, a lock — belongs to an object whose destructor releases it. Then it is released when the object goes out of scope, and that happens whether the function returned normally, returned early, or threw. The practical test is blunt: if you are typing delete, ask what should have owned that instead.

4 Rule 5

The destructor that quietly does not run 🧨

C.35 — A base class destructor should be either public and virtual, or protected and non-virtual.

The longest of the five, and the one whose absence is hardest to notice, because the broken version runs perfectly well for years:

struct Shape {
    virtual double area() const = 0;
    ~Shape();                       // ✗ not virtual
};

std::unique_ptr<Shape> s = std::make_unique<Circle>(2.0);
// when s goes out of scope: ~Shape() runs, ~Circle() does NOT

Deleting a derived object through a base pointer, when the base destructor is not virtual, is undefined behaviour — in practice the derived part is simply never cleaned up, so any resource it owned leaks silently. Lesson 7.5 showed exactly this. The fix is one word:

virtual ~Shape() = default;      // ✓ public and virtual

The rule's second half covers the other case. If nobody is ever meant to delete through a base pointer, you can say so by making the destructor protected and non-virtual — which removes the cost of a virtual destructor and makes the mistake impossible to write. Either arrangement is safe; it is the third one — public and non-virtual, on a class with virtual functions — that quietly leaks.

Notice what these five have in common. None of them is about style, brace placement, or naming. Each one closes a hole through which real programs lose data, leak memory, or behave differently on different machines — and each has a cost of roughly one word of typing. That is the bar the Core Guidelines set for themselves, and it is why the document is worth returning to: a rule earns its place by preventing something, not by looking tidy.
5 Having it checked for you

clang-tidy, and the finished safety net 🤖

The best part is that you mostly do not have to remember any of this. clang-tidy reads your code and reports the rules you are breaking, by number:

clang-tidy src/*.cpp -checks='cppcoreguidelines-*' -- -std=c++11

task.cpp:14:9: warning: variable 'count' is not initialized
    [cppcoreguidelines-init-variables]
shape.h:5:5: warning: destructor of 'Shape' is public and non-virtual
    [cppcoreguidelines-virtual-class-destructor]

That is the same relationship as 12.5's warnings and sanitizers, one level up: a tool that has read the rulebook so you do not have to. It is a separate program from your compiler, part of the LLVM project, and it slots into the CMake project from 12.6 in a couple of lines.

So the finished picture for a small project looks like this — and every piece of it came from one of the last four lessons:

One caution, straight from the document's own philosophy (P.1, "express ideas directly in code"). The guidelines are guidance, not law. Each rule states its reasoning, and there are situations where the reasoning does not apply — the rules say so themselves, with exceptions listed. What they are not is a stick for code review. "That breaks F.16" is a place to start a conversation about why, not a verdict.

8 Mistakes, exercises, recap

Wrap up 🏆

Three mistakes to avoid 🚨

📕
Trying to read all of it The Core Guidelines are a reference, not a book. Nobody has read them end to end. Learn a handful, and use the rest the way you use a dictionary — when a specific question comes up, search the rule ID.
⚖️
Quoting a rule number instead of a reason Every rule states why it exists, and most list exceptions. "This breaks F.16" tells a colleague nothing they can act on; "this copies the whole vector on every call" does. If you cannot explain the reason, you do not yet know whether the rule applies here.
🌍
Trusting old advice you find online An enormous amount of C++ material predates C++11 and recommends things — manual new/delete pairs, raw owning pointers, hand-written copy constructors everywhere — that are now the wrong answer. When something you read conflicts with these guidelines, check the date on it.

Practice exercises 💪

Easy Audit your own code. Open the to-do app from 12.1 and check it against exactly these five rules, by hand. Every variable initialised at the point it is declared? Every parameter you do not modify taken as const& or a cheap value? Any bare new? Any base class with virtual functions and a non-virtual destructor? Fix what you find.
Medium Prove C.35 to yourself. Write a Base with a virtual function and a non-virtual destructor, and a Derived that owns a std::vector<int> and prints a message from its destructor. Delete a Derived through a Base* and watch which message appears. Then run the same program under -fsanitize=address and read the leak report. Add virtual and watch both go away.
Stretch Look one up. Open the Core Guidelines and find a rule in a section this book did not cover — Con (constants), Enum, or SL (the standard library). Read its reasoning and its exceptions, then find a place in your own code where it applies and apply it. Being able to navigate the document is worth more than memorising any particular rule from it.

🎓 What to remember

  • The C++ Core Guidelines (Stroustrup and Sutter, at isocpp.github.io/CppCoreGuidelines) are the maintained answer to "what does good modern C++ look like?" — numbered, reasoned, and largely machine-checkable.
  • ES.20 — always initialise an object. One character, one whole class of bug gone.
  • P.10 — prefer immutable data; make const the default and remove it only where you must.
  • F.16 — cheap types by value, everything else by const&, and plain & only when you mean to modify.
  • R.1 — resources belong to objects. If you are typing delete, ask what should have owned it.
  • C.35 — a base class destructor is public and virtual, or protected and non-virtual. Never public and non-virtual.
  • clang-tidy checks most of them for you, and completes the safety net: rules while writing, warnings while compiling, sanitizers while running, tests on every build.
