🧰 PART XII · PUTTING IT ALL TOGETHER

Warnings & Sanitizers

Your compiler will cheerfully build a program that reads past the end of an array and prints nonsense. It is not being unhelpful — you never asked it to look. Two switches change that: warnings, which read your code before it runs, and sanitizers, which watch it while it runs. Between them they catch most of the bugs that make C++ frightening.

1 Why this matters

The program that lied 🤫

Here is a program with one wrong character in it. Read it, then guess what it prints.

#include <iostream>

int main() {
    int scores[3] = { 10, 20, 30 };
    int total = 0;
    for (int i = 0; i <= 3; i++)   // <= walks one step too far
        total += scores[i];
    std::cout << "total = " << total << "\n";
}

It should print 60. Compiled and run on the machine this lesson was written on, it printed:

$ g++ -std=c++11 -o scores scores.cpp
$ ./scores
total = 1027386684

No error. No warning. Exit code 0 — the shell was told everything went fine. The loop read scores[3], which is one slot past the end of the array, and whatever bytes happened to sit there became part of the total. Run it again tomorrow and you may get 60, or a crash, or a different wrong number.

This is the thing beginners find hardest to believe about C++: "it compiled" and "it works" are unrelated claims. The language trades safety for speed — nobody checks your array index unless you ask. The good news is that asking is two flags long, and this lesson is about those flags. Everything here is free, built into the compiler you already have, and takes about a minute to adopt permanently.
2 Turn the warnings on

-Wall, -Wextra, -Werror 🚦

Your compiler has a large collection of "are you sure?" checks that are off by default. You switch the useful ones on with two flags:

g++ -std=c++11 -Wall -Wextra -o app main.cpp

-Wall is badly named — it is not "all warnings", it is "the warnings almost everyone wants". -Wextra adds a second, pickier batch. Together they are the accepted baseline; there is no serious C++ project that builds without them. Here is one they catch:

std::vector<int> v{ 1, 2, 3 };
for (int i = 0; i < v.size(); i++)      // int vs size_type
    std::cout << v[i] << " ";
warning: comparison of integer expressions of different signedness:
         'int' and 'std::vector<int>::size_type' {aka 'long unsigned int'}
         [-Wsign-compare]
    6 |     for (int i = 0; i < v.size(); i++)
      |                     ~~^~~~~~~~~~

Notice the shape of the message: the file and line, the problem in one sentence, the name of the warning in brackets, and a caret pointing at the exact expression. That bracketed name is searchable — -Wsign-compare pasted into a search engine explains the whole issue.

The next step: -Werror. It turns every warning into a hard error, so the build fails instead of scrolling past. That sounds harsh, and it is exactly the point — a warning you can ignore is a warning you will ignore, and then a hundred of them pile up and you stop reading any of them. Turn it on early, while your project is small enough that there is nothing to clean up.
3 The optimisation catch

Why -O1 finds more than -O0 🔎

Here is a trap worth knowing about, because it makes people think warnings do not work. This program uses a variable that was never given a value:

int count;                 // never initialised
for (int i = 0; i < 5; i++)
    count += i;              // adding to garbage
std::cout << count;

Compile it with -Wall -Wextra and GCC says nothing at all. Add -O1 and it says:

warning: 'count' is used uninitialized [-Wuninitialized]
    4 |     int count;
      |         ^~~~~

Why the difference? Finding an uninitialised read means tracing every path the value could take through the function, and that analysis is something the compiler only performs when it is already analysing your code for optimisation. At -O0 it never looks, so it never finds it.

So the everyday line to build with is:

g++ -std=c++11 -Wall -Wextra -Werror -O1 -g -o app main.cpp

-O1 to wake up the deeper warnings, and -g so that when something does go wrong you get file names and line numbers instead of hexadecimal. Type it once into your build script and forget it.
Worth being honest about the limit: warnings are guesses made by reading the source. The array bug from section 1 — i <= 3 on a 3-element array — slips past -Wall -Wextra completely, at every optimisation level. Nothing in the text is obviously wrong; the mistake only exists at the moment the program runs. That is precisely the gap the next section fills.
4 Sanitizers

A checker that runs with your program 🧪

A sanitizer is a different idea. Instead of reading your source, the compiler rewrites your program, wrapping every memory access in a check, and the checks run as the program runs. The moment something is wrong, it stops and tells you exactly where.

One flag switches it on:

g++ -std=c++11 -g -fsanitize=address -o scores scores.cpp
./scores

Running our silently-wrong program from section 1 under AddressSanitizer:

==4031==ERROR: AddressSanitizer: stack-buffer-overflow
READ of size 4 at 0x7fa63670002c thread T0
    #0 0x5624622 in main scores.cpp:7

Address 0x7fa63670002c is located in stack of thread T0
  at offset 44 in frame
    #0 0x562462 in main scores.cpp:3
  This frame has 1 object(s):
    [32, 44) 'scores' <== overflows this variable

Read that last part slowly, because it is doing a lot of work for you. It names the kind of bug (stack-buffer-overflow), what you did (a 4-byte read), the exact source line (scores.cpp:7), and which variable you ran off the end of ('scores', which occupies bytes 32–44, and you touched byte 44). That is more than most debuggers would tell you after an hour.

AddressSanitizer catches the whole family of memory mistakes that C++ is notorious for: reading or writing past the end of an array (on the stack or the heap), using a pointer after delete, deleting the same pointer twice, and — when the program exits — anything you allocated and never freed, reported as a leak with the line that allocated it. Every one of those is otherwise invisible.
5 Which tool catches what

Reading the code vs watching it run 🎯

Its sibling, UndefinedBehaviorSanitizer, watches for operations the language says are meaningless — signed overflow, shifting an int by more bits than it has, dereferencing a null pointer, a bad cast:

g++ -std=c++11 -g -fsanitize=undefined -o app main.cpp

int value = 1;
std::cout << (value << 40);   // a 32-bit int shifted 40 places

main.cpp:6:25: runtime error: shift exponent 40 is too large
                for 32-bit type 'int'

You can run both at once — -fsanitize=address,undefined — and for a small program you should. Here is the whole mental model in one table:

ToolWhen it looksWhat it finds
-Wall -Wextrawhile compilingsuspicious code — unused variables, mixed signs, uninitialised reads
-fsanitize=addresswhile runningbad memory — overflows, use-after-free, double delete, leaks
-fsanitize=undefinedwhile runningmeaningless operations — overflow, bad shifts, null dereference

They do not overlap much, which is why you want all three. Warnings are free but can only see what is written down; sanitizers see what actually happened but only on the paths your program actually took — so they find more the more you exercise the code.

One rule about shipping. Sanitizers make a program roughly twice as slow and much hungrier for memory, because every access now costs a check. That is a wonderful trade while you are developing and a terrible one for the copy you hand to someone else. So: build with them while you work and while you test, and build the release copy without them. This is exactly the sort of thing a build file should remember for you — which is the next lesson.

8 Mistakes, exercises, recap

Wrap up 🏆

Three mistakes to avoid 🚨

🙈
Letting warnings accumulate Once a build prints forty warnings, nobody reads the forty-first — and that is the one that mattered. Add -Werror while the project is small, so the count can never climb above zero.
🩹
Silencing a warning with a cast Writing (int)v.size() to make -Wsign-compare shut up hides the question instead of answering it. Fix the types — use std::size_t for the index, or a range-for and no index at all.
🚢
Shipping a sanitizer build Sanitizers roughly halve your speed and inflate memory use. They belong in the build you develop and test with, never in the copy you hand to someone else.

Practice exercises 💪

Easy Reproduce section 1. Type in the scores program with i <= 3 and build it three ways: plain, with -Wall -Wextra, and with -fsanitize=address. Write down what each one told you. This is the single most convincing five minutes in this part of the book.
Medium Make a leak report. Write a program that does int* p = new int(42);, prints *p, and never deletes it. Run it under -fsanitize=address and find, in the report, the line number where the leaked memory was allocated. Then fix it two ways — with delete, and with a std::unique_ptr — and confirm the report goes quiet.
Stretch Sanitize a capstone. Take the to-do app from 12.1 and rebuild it with -Wall -Wextra -O1 -g -fsanitize=address,undefined. Exercise every menu option, including the ones you have not touched since you wrote it, then quit properly so the leak check runs at exit. Fix whatever it reports — and if it reports nothing, you have learned something reassuring about the habits you have been building.

🎓 What to remember

  • Compiling cleanly proves nothing — the array bug in section 1 builds without a murmur and prints garbage.
  • -Wall -Wextra is the baseline, -Werror keeps the count at zero, and -O1 is what wakes up the deeper checks like -Wuninitialized.
  • Sanitizers instrument the running program: -fsanitize=address for memory (overflows, use-after-free, leaks), -fsanitize=undefined for meaningless operations.
  • Warnings read the code; sanitizers watch it run. Different jobs, small overlap — use both.
  • Everyday build line: -std=c++11 -Wall -Wextra -Werror -O1 -g -fsanitize=address,undefined while developing; drop the sanitizers for the copy you ship.
