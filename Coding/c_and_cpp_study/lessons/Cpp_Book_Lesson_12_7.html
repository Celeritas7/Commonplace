🧰 PART XII · PUTTING IT ALL TOGETHER

Your First Unit Test

So far you have checked your programs by running them and looking at the output. That works right up until the program is big enough that you cannot check all of it, which is roughly the point at which you stop wanting to change anything. A unit test is that check written down once and run by a machine forever.

1 Why this matters

The input you never tried 👀

Here is a small function from the to-do app: it strips the spaces off both ends of a task title.

// task.cpp
std::string trim(const std::string& s) {
    std::size_t b = s.find_first_not_of(' ');
    std::size_t e = s.find_last_not_of(' ');
    return s.substr(b, e - b + 1);
}

You test it the way you have been testing everything: put it in main, print the result, run it.

std::cout << "[" << trim("  buy milk  ") << "]\n";
// [buy milk]   ✓ looks right

It works. You move on. Two weeks later a user types a title that is nothing but spaces, and the program throws an exception and dies — because find_first_not_of returned npos and substr was handed a nonsense position. You never tried that input, because when you were testing by hand you were thinking about task titles, not about the strange ones.

That is the real problem with checking things by eye. It is not that it is slow — it is that you only ever check the cases you happen to think of, once, on the day you wrote the code. A unit test is the same check, written down, run automatically every single time you build. The awkward input you thought about on Tuesday is still being checked in March.
2 The mental model

A test is an assertion with a name ✅

A test framework is less magic than it sounds. Strip it back and a test is a named block containing assertions:

TEST_CASE("trim removes spaces from both ends") {
    CHECK(trim("  hello  ") == "hello");
    CHECK(trim("hello")     == "hello");
}

TEST_CASE("trim handles the empty and all-space cases") {
    CHECK(trim("")      == "");
    CHECK(trim("     ") == "");
}

That is the whole shape, and it will look the same in every framework you ever meet. TEST_CASE names a scenario in a sentence — so that a failure reads like a description of what broke, not like test_17 failed. CHECK states something that must be true.

The framework's job is to collect every TEST_CASE in your project, run them all, and report. It also supplies main, which is why a test build has two entry points and you build it as a separate executable from your actual program.

Why CHECK rather than plain if? Because when it fails you want to be told what the values were, not just that something was wrong. A framework's macro captures the expression before evaluating it, so it can print both the code you wrote and the values it saw. Rolling that by hand is possible and thoroughly not worth your time.
3 One header, one test file

doctest in five minutes 📄

Two frameworks dominate small C++ projects: doctest and Catch2. Their syntax is nearly identical — the code above compiles under either. doctest is the lighter of the two and, for a first test, has one very attractive property: it is one header file. Download doctest.h, drop it in a tests/ folder, and you are done. No installer, no package manager, no build step.

todo/
├── CMakeLists.txt
├── src/
│   ├── main.cpp
│   ├── task.h
│   └── task.cpp
└── tests/
    ├── doctest.h          # the framework, one file
    └── test_task.cpp      # your tests

The test file needs one line of ceremony at the top, which asks doctest to provide main:

#define DOCTEST_CONFIG_IMPLEMENT_WITH_MAIN
#include "doctest.h"
#include "task.h"

TEST_CASE("trim removes spaces from both ends") {
    CHECK(trim("  hello  ") == "hello");
    CHECK(trim("hello")     == "hello");
}

Then build it like any other program — your test file plus the source files it tests, but not your main.cpp:

g++ -std=c++11 -Isrc -Itests -o run_tests \
    tests/test_task.cpp src/task.cpp
./run_tests

[doctest] test cases: 2 | 2 passed | 0 failed | 0 skipped
[doctest] assertions: 4 | 4 passed | 0 failed |
[doctest] Status: SUCCESS!
4 Reading a failure

What a good report tells you 🔍

Now the interesting half. Break trim so it only strips the left-hand side:

return s.substr(b);        // oops — left only
$ ./run_tests

test_task.cpp:5:
TEST CASE:  trim removes spaces from both ends

test_task.cpp:6: ERROR: CHECK( trim("  hello  ") == "hello" ) is NOT correct!
  values: CHECK( hello   == hello )

[doctest] test cases: 2 | 1 passed | 1 failed | 0 skipped
[doctest] assertions: 4 | 3 passed | 1 failed |
[doctest] Status: FAILURE!

Look at how much that hands you. The scenario that broke, in the sentence you wrote. The exact line. The expression as you typed it. And the values — hello   against hello, trailing spaces and all, which points straight at the half of the function you got wrong. You did not have to add a single cout.

And now the original bug. Restore the all-spaces case as a test and run it against the very first version of trim:

test_task.cpp:11: ERROR: CHECK( trim("") == "" ) THREW exception:
  "basic_string::substr: __pos (which is 18446744073709551615)
   > this->size() (which is 0)"
A test that throws is caught and reported like any other failure rather than taking the whole run down with it — so one broken case does not hide the other twenty. And that enormous number is worth recognising on sight: it is std::string::npos, which is size_t(-1). Whenever you see 18446744073709551615 in an error message, some search returned "not found" and nobody checked.
5 Wiring it into the build

add_test and ctest ⚙️

Running tests by hand has the same flaw as testing by hand: you have to remember. So hang them off the build. Building on the CMake file from 12.6, three ideas do it.

First, put the code under test into a library so that both your program and your tests can link against it — otherwise you would compile task.cpp twice, in two different ways:

add_library(task src/task.cpp)
target_include_directories(task PUBLIC src)

add_executable(todo src/main.cpp)
target_link_libraries(todo PRIVATE task)

PUBLIC on that include directory means "anything that links to task also gets src on its include path" — so neither todo nor the tests have to repeat it. That is the one real difference between PUBLIC and PRIVATE: whether the setting is passed on to whoever links you.

Then the test executable, and one line registering it with CTest — CMake's test runner:

enable_testing()

add_executable(run_tests tests/test_task.cpp)
target_include_directories(run_tests PRIVATE tests)
target_link_libraries(run_tests PRIVATE task)

add_test(NAME unit_tests COMMAND run_tests)
$ cmake --build build
$ cd build && ctest --output-on-failure

    Start 1: unit_tests
1/1 Test #1: unit_tests .......................   Passed    0.00 sec

100% tests passed, 0 tests failed out of 1
--output-on-failure is the flag to type every time: silence when everything passes, the framework's full report the moment something does not. That combination — build, then ctest — is what continuous integration servers run on every push, and it is what you should run before every commit. Two commands, and the machine now checks everything you have ever thought to check.

8 Mistakes, exercises, recap

Wrap up 🏆

Three mistakes to avoid 🚨

🌤️
Only testing the happy path trim(" hello ") was never the input that broke. Bugs live in the awkward cases: empty, one element, all-spaces, negative, the maximum value, the thing that is not found. When you write a test, spend most of your thinking on the edges.
🕸️
Testing five things in one TEST_CASE When it fails you are told the name of the case, so the name should describe one behaviour. "trim handles the empty and all-space cases" tells you where to look; "task tests" does not.
👻
Never watching a test fail A test that has only ever passed might be testing nothing at all — a typo in the expected value, a function never called. Break the code on purpose once and confirm the test goes red. A green suite is only meaningful if red was possible.

Practice exercises 💪

Easy Test something you already wrote. Pick any small function from an earlier lesson that takes a value and returns one. Fetch doctest.h, write two TEST_CASEs for it — one ordinary input, one awkward one — and build the test executable by hand with the g++ line from section 3.
Medium Watch it go red. With those tests passing, deliberately break the function — flip a comparison, drop a + 1. Run the tests, then read the report properly: which case, which line, which values. Fix it and watch it go green. Do this once and the whole idea stops being abstract.
Stretch Wire it into the build. Take your CMake project from 12.6 and restructure it as in section 5: an add_library for the code, an executable for the program, another for the tests, and add_test to register it. Confirm that ctest --output-on-failure runs them. Then add the sanitizer lines from 12.6 to the test target as well — a test suite running under AddressSanitizer is the strongest safety net a small project can have.

🎓 What to remember

  • Checking by eye only checks what you thought of, once. A unit test is that same check, run automatically forever.
  • A test is a TEST_CASE with a sentence for a name, containing CHECK assertions. Same shape in every framework.
  • doctest is a single header — drop it in tests/, #define DOCTEST_CONFIG_IMPLEMENT_WITH_MAIN, and build the tests as their own executable.
  • Read failures properly: they give you the case, the line, the expression and the actual values.
  • Wire it in: add_library for the shared code, enable_testing() plus add_test, then ctest --output-on-failure.
  • Fixed a bug? Write the failing test first. That is how it stays fixed.
