Building with CMake

Every program in this book has been one file, built with one g++ line you typed by hand. Real projects are many files with a build line nobody can remember. CMake is where you write that line down once — about twenty lines, most of which you will copy from this lesson forever.

1 Why this matters

When one g++ line stops being enough 📚

Split the to-do app from 12.1 into the shape a real project takes — a header, its implementation, and a main — and the build line stops being something you can type from memory:

todo/
├── CMakeLists.txt
└── src/
    ├── main.cpp
    ├── task.h
    └── task.cpp
g++ -std=c++11 -Wall -Wextra -Werror -O1 -g -Isrc \
    -fsanitize=address,undefined \
    src/main.cpp src/task.cpp -o todo

That already has eleven things to remember, and it grows every time you add a file. Worse, it rebuilds everything every time — change one comment in task.cpp and you recompile main.cpp too. On a project of five files nobody notices. On fifty, you notice constantly.

And there is a subtler problem. If you edit task.h, both .cpp files need rebuilding, because both include it. Nothing in that g++ line knows that. Keeping track of which files depend on which headers, by hand, is exactly the kind of bookkeeping people get wrong at 11pm.

A build system is a program that solves those three problems: it remembers the command, it rebuilds only what actually changed, and it works out the header dependencies for you. CMake is the one the C++ world settled on. It is not the prettiest tool you will ever use, but it is the one that opens every project you will ever clone, and the twenty lines you need are genuinely twenty lines.
2 The mental model

CMake generates a build system 🏗️

Here is the one useful thing to understand before any syntax: CMake does not build your program. It reads your CMakeLists.txt and generates a build system — Makefiles on Linux, a Visual Studio solution on Windows, Ninja files if you ask — and that builds your program.

So there are always two steps, and they answer two different questions:

StepCommandQuestion it answers
configurecmake -S . -B buildwhich compiler, which options, what needs building?
buildcmake --build buildgo and compile whatever is out of date

-S . says the source is here; -B build says put everything you generate in a folder called build. You run the first command once — or again whenever you edit CMakeLists.txt — and the second one every time you change code.

Why the separate build/ folder matters. Everything CMake and the compiler produce lands in there and nowhere else, so your source folder stays exactly as clean as you wrote it. That means build/ is completely disposable: if anything ever gets into a confusing state, delete the folder and configure again, and you have lost nothing. It also means build/ goes straight into your .gitignore — never commit it. This arrangement has a name people will use around you: an out-of-source build.
3 The file itself

Nine lines, line by line 📄

This is the file. It builds the project from section 1, and it is close to the shortest thing that deserves to be called complete:

# CMakeLists.txt
cmake_minimum_required(VERSION 3.16)
project(todo LANGUAGES CXX)

set(CMAKE_CXX_STANDARD 11)
set(CMAKE_CXX_STANDARD_REQUIRED ON)

add_executable(todo src/main.cpp src/task.cpp)
target_include_directories(todo PRIVATE src)
target_compile_options(todo PRIVATE -Wall -Wextra)

Line by line:

  • cmake_minimum_required — the oldest CMake that understands this file. Pick something recent; 3.16 is a safe floor.
  • project — names the project and says it is C++ (CXX). This is also where CMake goes looking for your compiler.
  • CMAKE_CXX_STANDARD 11 — this book's baseline. ..._REQUIRED ON means fail if the compiler cannot do C++11, rather than quietly falling back.
  • add_executable — the important one. It says "there is a thing to build called todo, made from these source files". Headers are not listed; CMake finds those itself.
  • target_include_directories — where to look for #include "task.h". The old -I flag, attached to this target only.
  • target_compile_options — the flags from 12.5, again attached to this target only.
Notice the word target at the front of three of those commands, and the word PRIVATE inside them. That is the whole style of modern CMake: settings belong to a target, not to the whole directory. There are older commands (include_directories, add_definitions) that apply to everything at once, and you will meet them in old projects — they cause trouble the moment a project has two targets that need different flags. PRIVATE means "these flags are for building this target, and are not passed on to anything that links against it".
4 The daily loop

Configure once, build often ⚙️

Now the payoff. Configure once:

$ cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug
-- The CXX compiler identification is GNU 13.3.0
-- Configuring done (0.2s)
-- Generating done (0.0s)
-- Build files have been written to: /home/you/todo/build

Then build:

$ cmake --build build
[ 33%] Building CXX object CMakeFiles/todo.dir/src/main.cpp.o
[ 66%] Building CXX object CMakeFiles/todo.dir/src/task.cpp.o
[100%] Linking CXX executable todo
[100%] Built target todo

Change one line in task.cpp and build again:

$ cmake --build build
[ 33%] Building CXX object CMakeFiles/todo.dir/src/task.cpp.o
[ 66%] Linking CXX executable todo
[100%] Built target todo

main.cpp was left alone — it had not changed. Now edit task.h instead, the header both files include:

$ cmake --build build
[ 33%] Building CXX object CMakeFiles/todo.dir/src/main.cpp.o
[ 66%] Building CXX object CMakeFiles/todo.dir/src/task.cpp.o
[100%] Linking CXX executable todo

Both came back, because both include that header. Nobody told CMake about that relationship — it scanned the #includes and worked it out. That is the piece you cannot reasonably do by hand, and the single best reason to stop typing g++ lines.

5 Debug and Release

Two builds from one source 🎚️

Remember the rule from the last lesson: warnings and sanitizers while you develop, neither in the copy you ship. CMake has that idea built in as the build type, and the two standard ones already carry sensible flags:

Build typeFlags CMake addsFor
Debug-gdeveloping — real line numbers when things break
Release-O3 -DNDEBUGthe copy you hand over — optimised, assertions off

You pick one when you configure, and you can keep two build folders side by side and switch between them freely:

cmake -S . -B build     -DCMAKE_BUILD_TYPE=Debug
cmake -S . -B build-rel -DCMAKE_BUILD_TYPE=Release

To attach the sanitizers to the Debug build only, add two lines. The $<...> spelling is a generator expression — a condition evaluated when the build files are written:

# only in Debug builds: the checks from 12.5
target_compile_options(todo PRIVATE $<$<CONFIG:Debug>:-fsanitize=address,undefined>)
target_link_options(todo PRIVATE $<$<CONFIG:Debug>:-fsanitize=address,undefined>)

Sanitizers need the flag at both compile and link time — a genuinely common thing to get half-right and then wonder why the checks never fire.

That is the moment the twenty lines start paying you back. You can no longer forget the warnings, no longer accidentally ship a sanitized binary, and no longer half-remember which folder had which flags — the file remembers, and it remembers on your colleague's machine and on your own laptop in six months. Everything past this point is more of the same: add_library for code shared between programs, target_link_libraries to join them, find_package to pull in something installed on the system. Look those up when you need them; the shape stays identical.

7 Quick check

One question 🎯

You edit task.h, which both main.cpp and task.cpp include, then run cmake --build build. What gets recompiled?
Hint: a header is pasted into every file that includes it — so changing it changes all of them.
8 Mistakes, exercises, recap

Wrap up 🏆

Three mistakes to avoid 🚨

🗑️
Committing the build/ folder It is generated output, it is large, and it is specific to your machine — full of absolute paths that mean nothing anywhere else. Add build/ to .gitignore on day one. If a build ever behaves strangely, deleting the whole folder and configuring again is the correct first move, not a last resort.
🧩
Listing headers in add_executable Only .cpp files are compiled; CMake discovers the headers by scanning your #includes. Listing task.h there is harmless but pointless — and forgetting to list it does not break dependency tracking, which is the thing beginners usually fear.
🔗
Adding -fsanitize=... to compile options only Sanitizers need the flag when linking too, or the runtime library never gets attached and the checks silently never fire. Set both target_compile_options and target_link_options.

Practice exercises 💪

Easy Build something you already wrote. Take any single-file program from this book, put it in src/main.cpp, and write the nine-line CMakeLists.txt from section 3 around it. Configure, build, run. Then delete build/ entirely and do it again — proving to yourself that nothing important lives in there.
Medium Split it in two. Move one function out of main.cpp into src/util.h and src/util.cpp, add the new .cpp to add_executable, and rebuild. Now edit only util.cpp and watch which files recompile; then edit only util.h and watch again. The difference between those two runs is the whole point of this lesson.
Stretch Two builds, one source. Configure build/ as Debug with the sanitizer lines from section 5, and build-rel/ as Release. Deliberately break something — read one past the end of a vector — and run both binaries. The Debug one should report the bug and stop; the Release one will most likely print nonsense and carry on. That contrast is the reason build types exist.

🎓 What to remember

  • CMake generates a build system; it does not compile anything itself. Two steps, always: cmake -S . -B build, then cmake --build build.
  • Everything generated lives in build/ — disposable, gitignored, safe to delete whenever you like.
  • The nine lines in section 3 are a complete project file: minimum version, project, standard, add_executable, and the target_ commands for includes and flags.
  • Prefer the target_* commands with PRIVATE — settings belong to a target, not to a whole directory.
  • Incremental builds and header dependencies come free, and that is the part you could not sensibly do by hand.
  • CMAKE_BUILD_TYPE gives you Debug (-g) and Release (-O3 -DNDEBUG); hang the sanitizers off Debug only, at both compile and link.
