References and Pointers

Every variable so far has owned its own box of memory. Now for the two ways to talk about someone else's box: a reference, which is simply a second name for it, and a pointer, which is a variable holding its address. Get these straight and the rest of C++ — functions that change their arguments, classes, this — stops looking like punctuation soup.

1 Why this matters

A copy is not the original 💭

Every declaration you have written so far makes a brand-new box and fills it:

std::string a = "a long piece of text…";
std::string b = a;   // a second, complete copy of the text
b += "!";          // b changed; a is untouched
That is exactly right most of the time — and it costs you two things. Copying a big object is real work (every character of that string gets duplicated), and a copy is a different object, so changing it can never change the original. Sometimes you want the opposite: to work with the very same object under a different name, or to hold on to where an object lives so you can find it later.

C++ gives you two tools for that. A reference is a second name for an existing object. A pointer is a variable whose value is an address. They overlap enough to be confusing and differ enough to matter, so this lesson takes them one at a time — and by the end you will know which to reach for.

2 The mental model

Boxes, labels, and addresses 📦

Picture memory as a street of numbered boxes. A variable is a box with a label stuck on it:

A value is a box of its own, holding its own contents.
A reference is a second label stuck on a box that already exists. Nothing new is stored — the box just answers to two names now.
A pointer is a box of its own, but what it holds is the house number of another box. To reach the thing itself you have to walk to that address.

Those last two columns are the whole difference. A reference is a promise: there is definitely an object here, and it will always be the same one. A pointer promises nothing — it may point somewhere, may point nowhere, and may point somewhere else a line later. Choose whichever promise matches your situation.

3 References

A permanent second name 🔗

Write & after the type to declare a reference. It must be attached to something at the moment it is born:

int x = 10;
int& r = x;        // r is another name for x

r = 20;             // writes into x
std::cout << x;      // 20

Notice there is no special syntax for using a reference. You do not unwrap it or follow it — you just use r exactly as you would use x, because it is x. That is the pleasant part.

🚨 Here is the one thing everybody gets wrong. Once r is attached to x, it is attached for life. So what does r = y; do? Not what it looks like: it does not point r at y. It copies y's value into the box r names — that is, into x. There is no syntax in C++ for re-seating a reference, because that is precisely the guarantee a reference makes.

Two smaller rules follow from the same guarantee. int& r; on its own will not compile — a reference with nothing to refer to is a contradiction. And a reference can never be null, which is why code that takes a reference never has to check for one.

4 Pointers

A variable that holds an address 📍

Two operators do the work. & in front of an object asks "what is your address?", and * in front of an address says "give me what lives there":

int x = 10;
int* p = &x;       // p holds the address of x

std::cout << *p;    // 10  — follow the address
*p = 20;            // write through it: x is now 20

int y = 99;
p = &y;              // re-seated: p now holds y's address
p = nullptr;        // or nothing at all (C++11)
Both symbols do two different jobs depending on where they appear, and that is the single biggest source of confusion. In a declaration, int& r and int* p describe what kind of thing you are making. In an expression, &x takes an address and *p follows one. Read the line and ask "am I declaring, or am I doing?" — the symbols mean different things in each case.

nullptr is the value meaning "deliberately pointing at nothing." It is worth using precisely because you can test for it: if (p) { … } is true when p points somewhere and false when it is null. A pointer you have not initialised at all is far worse than a null one — it holds whatever junk was in that memory, and following it is undefined behaviour.

5 Choosing between them

The arrow, and which tool when ⚖️

One more piece of syntax you will meet constantly from Part VI onward. When a pointer points at something with members, reaching a member takes two steps — follow the pointer, then pick the member — and -> is the shorthand for both:

(*p).size()    // follow p, then call size()
p->size()      // identical, and this is what everyone writes

With the mechanics out of the way, the practical question is which to reach for. This table is the short answer, and it will carry you a long way:

SituationReach for
A small value you only need to read (int, char, bool)a plain copy
Something big you only need to read (a string, a container)const T&
Something you must be able to modify, and it definitely existsT&
Something that might be absent, or that you need to re-aim laterT*
Modern C++ leans on references much harder than on raw pointers, and the table shows why: most of the time you either want a cheap copy or you want to touch an object that certainly exists. The pointer earns its place in exactly one situation — when "nothing here" is a legitimate answer, or when the thing you are looking at needs to change over time. Part VIII will add smart pointers for the cases where you also own what you point at.

8 Mistakes, exercises, recap

Wrap up 📚

Three mistakes to avoid 🚨

🔗
Expecting r = y; to re-aim the reference It never does. A reference is bound once, at birth, and stays bound; r = y copies y's value into whatever r already names. If you need something that can change target, you wanted a pointer.
💥
Following a pointer that points nowhere int* p; without an initialiser holds junk, and *p on it is undefined behaviour — often a crash, sometimes worse. Initialise every pointer, use nullptr for "nothing yet", and guard with if (p) before dereferencing anything that might be empty.
🎭
Writing int* p, q; and expecting two pointers The * binds to the declarator, not the type, so q is a plain int. Either write int *p, *q; or — much better — give each pointer its own line.

Practice exercises 💪

Easy Prove the alias. Declare int x = 5; and int& r = x;. Print both, set r = 42, print both again. Then declare int y = 7;, run r = y;, and print x, y and r. Convince yourself that the last line changed x and left r still attached to it.
Medium Walk a pointer. With int a = 1, b = 2;, declare int* p = &a;. Print *p, re-seat it with p = &b;, print *p again. Then set p = nullptr; and write an if (p) … else … that prints the value when there is one and "nothing to show" when there isn't.
Stretch The declaration trap. Write int* p, q; and hover over q in VS Code to see its real type. Now fix it two ways — once by moving the *, once by splitting the line — and check with static_assert(std::is_same<decltype(q), int*>::value, "not a pointer"); from <type_traits> that you actually got what you wanted.

🎓 What to remember

  • A reference is a second name for an object that already exists — no new storage, no special syntax to use it.
  • A reference is bound for life. r = y copies a value into the object r names; it never re-aims r.
  • A pointer is a variable holding an address. &x takes an address, *p follows one, and p->m is shorthand for (*p).m.
  • Only a pointer can be empty or re-aimed — that is exactly when to prefer one, and nullptr is how you say "nothing here."
  • Default to a copy for small values, const& for big read-only ones, T& when you must modify, T* when it might be absent.
