Chapter 2 — End-to-End Machine Learning Project

In one line
A real ML project is mostly not about the algorithm. You frame the business question, lock away an honest test set, explore and clean the data, wrap every preparation step in a reusable pipeline, compare models with cross-validation, tune the best one, and then keep watching it after it goes live.

1 · Working with real data & the project checklist book p. 35 ↗

The chapter plays out one project from start to finish: you are the new data scientist at a (made-up) real-estate company and must predict the median house value of each California district from 1990 census data (about 20,640 districts, 10 attributes, one of them text).

Practise on real data, not toy data. Real data has missing values, caps and odd units, and handling those is the actual skill.

Places to find datasets: the UCI repository, Kaggle, AWS open data, meta-portals that list other portals, and Wikipedia's list of ML datasets.

2 · Look at the big picture book p. 37 ↗

Frame the problem

  • Ask what the model is for. Here, its price estimate is one input to a downstream system that decides where to invest. The objective drives the framing, the algorithm, the metric and how much tuning effort is worth it.
  • Ask what the current solution is. Experts estimate prices by hand with rules, and are often off by more than 20%. That gives you a baseline to beat.
  • A data pipeline is a chain of processing components that usually run asynchronously and talk only through data stores. It is robust (a broken stage leaves the last output in place), but a silent failure makes the data stale unless you monitor it.

Select a performance measure

The usual regression metric is the root mean square error (RMSE). Because the errors are squared, large errors count much more:

$$\text{RMSE}(\mathbf X,h)=\sqrt{\frac1m\sum_{i=1}^{m}\big(h(\mathbf x^{(i)})-y^{(i)}\big)^2}$$

If there are many outlier districts, the mean absolute error (MAE) is a safer choice:

$$\text{MAE}(\mathbf X,h)=\frac1m\sum_{i=1}^{m}\big|h(\mathbf x^{(i)})-y^{(i)}\big|$$
  • Notation: $m$ = number of instances, $\mathbf x^{(i)}$ = feature vector of instance $i$ (label excluded), $y^{(i)}$ = its label, $\mathbf X$ = matrix with one row $(\mathbf x^{(i)})^\top$ per instance, $h$ = the prediction function or hypothesis, $\hat y^{(i)}=h(\mathbf x^{(i)})$.
  • Both metrics measure a distance between the prediction vector and the target vector, using a norm. RMSE matches the ℓ2 (Euclidean) norm; MAE matches the ℓ1 (Manhattan) norm.
$$\lVert\mathbf v\rVert_k=\big(|v_1|^k+|v_2|^k+\dots+|v_n|^k\big)^{1/k}\qquad \ell_0=\text{count of non-zeros},\quad \ell_\infty=\max_i|v_i|$$
The higher the norm index, the more it focuses on the biggest values. So RMSE is more sensitive to outliers than MAE. When outliers are very rare (bell-shaped errors), RMSE works well and is the usual choice.

Check the assumptions

Write down every assumption and verify it early. Example: if the downstream team only turned prices into "cheap / medium / expensive", the task would really be classification, and months of regression work would be aimed at the wrong target. Here they confirmed they need actual prices.

3 · Get the data book p. 42 ↗

Setting up the workspace: install Python, create an isolated environment (virtualenv / venv / conda), pip install Jupyter, NumPy, pandas, Matplotlib and scikit-learn, then start a notebook.

  • Write a small function that downloads and extracts the data. Then refreshing the data, or setting it up on another machine, takes one call (or a scheduled job).
  • First look with pandas: head(), info() (row count, dtypes, non-null counts), value_counts() for text columns, describe() (count, mean, std, min, percentiles/quartiles, max), and hist().

What the first look reveals

  • total_bedrooms has 207 missing values. That gets fixed later.
  • ocean_proximity is text with 5 repeated values, so it is a categorical attribute.
  • median_income is not in dollars. It was scaled (roughly units of $10,000) and capped at about 0.5 and 15. Preprocessed columns are fine; just find out how they were made.
  • The target, median_house_value, is capped at $500,000. A model may learn that prices never go higher. If the client needs predictions above the cap, either collect proper labels for those districts or remove them from both the training and test sets.
  • Features have very different scales, and many histograms are tail-heavy (long right tail). Both are handled later (scaling, and possibly a log transform).

Create a test set — now, before looking further

Data snooping bias: if you study the test set, your brain spots patterns in it and you pick a model that suits it. The test error then looks better than what you will see in production.

Split off the test set (typically 20%, less for very large datasets) before any real exploration, and don't look at it again until the very end.

Stratified splitKeeps important subgroups in the same proportions as the full data.

Stratified sampling: split the population into homogeneous groups called strata, then sample the right number from each stratum. Pure random sampling can give a skewed test set, especially when the dataset is not large compared with the number of attributes.

  • Experts say median income matters most, so the book builds an income_cat column with pd.cut (5 bins with edges 0, 1.5, 3, 4.5, 6, ∞) and stratifies on it.
  • Keep the number of strata small, so each stratum has enough instances. Too few rows in a stratum gives a biased estimate of its importance.
  • Tools: StratifiedShuffleSplit(n_splits=1, test_size=0.2, random_state=42), or simply train_test_split(..., stratify=df["income_cat"]).
  • Drop the helper income_cat column after splitting.

4 · Discover and visualise the data book p. 56 ↗

Explore the training set only, and work on a copy. If the training set is huge, explore a smaller sample.

Geographical scatter

  • Plotting longitude against latitude with a low alpha (e.g. 0.1) shows where districts are dense: the Bay Area, Los Angeles, San Diego and the Central Valley.
  • Adding s= (marker size = population) and c= (colour = price) with a colormap shows that price depends strongly on location and density, for example near the coast.
  • Idea: clustering could give new features such as the distance to the main cluster centres.

Looking for correlations

The standard correlation coefficient (Pearson's r) is between −1 and 1. df.corr() computes it for every pair of columns. Median income has by far the strongest link to the price (r ≈ 0.69).

$$r_{xy}=\frac{\sum_i (x_i-\bar x)(y_i-\bar y)}{\sqrt{\sum_i (x_i-\bar x)^2}\,\sqrt{\sum_i (y_i-\bar y)^2}}$$
r only measures linear relationships. A strong non-linear dependence (e.g. a U-shape) can have r ≈ 0. And r says nothing about the slope: height in cm and height in inches have r = 1.
  • pandas.plotting.scatter_matrix plots every chosen numeric column against every other one, with histograms on the diagonal. Pick a few promising columns, because n columns give n² plots.
  • The income vs. price scatter shows the $500k cap as a horizontal line, plus fainter horizontal lines (around $450k, $350k, $280k…). These are data quirks; consider removing those districts so models don't learn them.

Experimenting with attribute combinations

Raw totals mean little without context. Ratios are more informative:

  • rooms_per_household = rooms / households
  • bedrooms_per_room = bedrooms / rooms. Its correlation with price (≈ −0.26) is much stronger than either total alone. Fewer bedrooms per room tends to mean pricier homes.
  • population_per_household = population / households

Exploration doesn't need to be exhaustive. Build a prototype fast, then come back here with what the model teaches you.

5 · Prepare the data for ML algorithms book p. 62 ↗

Write preparation as functions and transformers, not manual edits. Then you can repeat it on fresh data, reuse it in later projects, apply it in production, and switch options on and off to see what helps.

Start again from a clean copy of the training set, and separate the predictors (X) from the labels (y), since they don't get the same transformations.

Data cleaning (missing values)

OptionpandasDownside
1. Drop the rows with missing valuesdropna(subset=[...])loses data
2. Drop the whole columndrop(col, axis=1)loses a feature
3. Fill with a value (0, mean, median…)fillna(median)must reuse the training median on test and live data

SimpleImputer(strategy="median") does option 3 properly. fit learns each column's median (stored in statistics_), and transform fills the gaps. It only works on numeric columns, so remove the text column first (or use a ColumnTransformer).

Fit the imputer on all numeric columns, not just the one with gaps today. New data may have missing values anywhere.

scikit-learn's design (worth memorising)

IdeaMeaning
EstimatorAnything that learns from data with fit(X[, y]). Settings passed to the constructor are hyperparameters (e.g. strategy).
TransformerAn estimator with transform(X). fit_transform does both, sometimes faster.

CompositionBuilding blocks combine, e.g. Pipeline.
Sensible defaultsA working baseline comes quickly.

Text & categorical attributes

  • OrdinalEncoder maps each category to an integer (the list is in categories_). Models then assume that nearby numbers mean similar categories, which only makes sense for ordered categories (bad < average < good).
  • One-hot encoding creates one 0/1 column per category (dummy attributes). OneHotEncoder returns a sparse matrix by default, which stores only the positions of the 1s. That saves a lot of memory when there are thousands of categories. Use .toarray() to get a dense array.
  • If a category has very many values, one-hot creates too many features. Replace it with meaningful numbers (e.g. distance to the ocean, a country's GDP) or with a learned embedding, an example of representation learning.

Custom transformers

scikit-learn uses duck typing: a class with fit (which returns self) and transform works in pipelines.

  • Inherit from TransformerMixin to get fit_transform for free.
  • Inherit from BaseEstimator (and use explicit constructor arguments, no *args/**kwargs) to get get_params/set_params, which grid search needs.
  • Put a hyperparameter on any preparation step you're unsure about (the book's example: add_bedrooms_per_room=True). Then a search can decide whether the step helps.
# minimal pattern (own example)
from sklearn.base import BaseEstimator, TransformerMixin
class RatioAdder(BaseEstimator, TransformerMixin):
    def __init__(self, add_ratio=True):
        self.add_ratio = add_ratio
    def fit(self, X, y=None):
        return self
    def transform(self, X):
        return np.c_[X, X[:, 0] / X[:, 1]] if self.add_ratio else X

Transformation pipelines

  • Pipeline([("name", step), ...]) runs the steps in order. Every step except the last must be a transformer. Names must be unique and must not contain __, because the double underscore is used later to address nested parameters ("imputer__strategy").
  • Calling pipeline.fit runs fit_transform on each step in turn and then fit on the last. The pipeline offers whatever methods the last step has (transform, predict…).
  • ColumnTransformer([("num", num_pipeline, num_cols), ("cat", OneHotEncoder(), cat_cols)]) sends each group of columns to its own transformer and joins the outputs side by side. It accepts pandas column names.
  • If sparse and dense outputs are mixed, the result is sparse only when the overall density is below sparse_threshold (default 0.3).
  • A step can be "drop" or "passthrough". Columns you don't list are dropped by default; change that with remainder=.
  • Before ColumnTransformer existed (0.20), people used FeatureUnion with a custom column-selector transformer, or the sklearn-pandas library.
• OneHotEncoder(sparse=False) is now sparse_output=False (renamed in 1.2). Add handle_unknown="ignore" so categories that appear only in new data don't raise an error.
• get_feature_names() became get_feature_names_out(), and it works on whole pipelines and ColumnTransformers. set_output(transform="pandas") makes transformers return DataFrames.
• Simple custom steps can be a FunctionTransformer(func, feature_names_out=...) instead of a class.
• Use root_mean_squared_error(y, ŷ) (1.4+) instead of np.sqrt(mean_squared_error(...)), and scoring="neg_root_mean_squared_error" in CV. (squared=False was deprecated.)
• train_test_split(..., stratify=y_cat) is a one-line stratified split.
• pandas 2: df.corr() no longer skips text columns silently; use df.corr(numeric_only=True).
• RandomForestRegressor: criterion="mse" is now "squared_error", n_estimators now defaults to 100 (it was 10), and the old min_impurity_split was removed.

6 · Select and train a model book p. 72 ↗

  1. LinearRegression: training RMSE ≈ $68.6k, while typical prices are $120k–$265k. That is underfitting. Fixes: a more powerful model, better features, or fewer constraints (this model has no regularisation to remove).
  2. DecisionTreeRegressor: training RMSE = 0. That is almost certainly severe overfitting, not perfection.
  3. So evaluate on data the model hasn't trained on, without touching the test set. Use a validation split or, better, cross-validation.

Cross-validation

K-fold cross-validation splits the training set into K folds, trains K times (each time on K−1 folds) and scores on the remaining fold. You get K scores, so you get a mean and a standard deviation, which tells you how precise the estimate is. The cost is K times the training time.

scores = cross_val_score(model, X, y, cv=10, scoring="neg_root_mean_squared_error")
rmse = -scores          # scorers follow "greater is better", so errors come back negated
Model (book's housing run)Training RMSE10-fold CV RMSEReading
Linear regression≈ 68.6k≈ 69.1k ± 2.7kunderfits
Decision tree0≈ 71.4k ± 2.4koverfits badly, worse than linear
Random forest≈ 18.6k≈ 50.2k ± 2.1kbest so far, but the big train/CV gap means it still overfits
  • A RandomForestRegressor averages many decision trees trained on random subsets. Building on many models like this is ensemble learning (chapter 7).
  • Try many model families quickly (SVMs with different kernels, a neural net…) without much tuning, and shortlist 2–5.
  • Save every experiment: hyperparameters, learned parameters, CV scores and predictions. Use joblib.dump(model, "m.pkl") / joblib.load (better than pickle for large NumPy arrays).

7 · Fine-tune your model book p. 75 ↗

Grid search

GridSearchCV(estimator, param_grid, cv=5, scoring=..., return_train_score=True) cross-validates every combination in the grid. param_grid can be a list of dicts, each explored separately.

  • Cost: the book's grid has 3×4 + 2×3 = 18 combinations × 5 folds = 90 training runs.
  • Results: best_params_, best_estimator_, cv_results_ (mean test score for each combination).
  • With refit=True (the default), the best combination is retrained on the whole training set.
  • No idea what value to try? Start with consecutive powers of 10, then zoom in.
  • If the best value sits at the edge of the grid (here max_features=8, n_estimators=30), extend the grid in that direction.
  • Preparation options can be hyperparameters too (whether to add a feature, how to impute, how to treat outliers). Put them in one pipeline and search over "step__param".

Randomized search

RandomizedSearchCV(estimator, param_distributions, n_iter=..., cv=...) samples random combinations. It is better when the search space is large:

  • Every run tries a new value for each hyperparameter, so 1,000 iterations explore 1,000 values per hyperparameter instead of a handful.
  • You set the compute budget directly with n_iter.

Ensembles

Combining your best models often beats the best single one, especially when they make different kinds of errors. Details in chapter 7.

Analyse the best models and their errors

  • feature_importances_ of a random forest ranks the inputs. In the book, median income comes first, then the INLAND category and population per household.
  • Drop features that don't help (e.g. most one-hot ocean categories), and look at the specific errors to find missing features or outliers to clean.

Evaluate on the test set — once

  • Run the fitted pipeline on the test set with transform(), never fit_transform(), then compute the RMSE (≈ $47.7k in the book).
  • A single number may not be enough to justify a launch. Add a 95% confidence interval for the RMSE, using the t-distribution over the squared errors $e_i=(\hat y_i-y_i)^2$:
$$\text{CI}_{\text{RMSE}}=\sqrt{\;\bar e\;\pm\;t_{0.975,\,m-1}\cdot\frac{s_e}{\sqrt m}\;}\qquad\texttt{scipy.stats.t.interval(0.95, m-1, loc=e.mean(), scale=stats.sem(e))}$$
The test score is often a little worse than the CV score after heavy tuning. Do not tweak hyperparameters to improve the test number; those gains won't carry over to new data.

Pre-launch: present what you learned, what worked and what didn't, your assumptions and limitations, with clear visuals and one-line findings ("median income is the top predictor"). Even a model that only matches the experts can be worth launching if it frees their time.

8 · Launch, monitor, and maintain book p. 80 ↗

Deploy

  • Polish the code, write tests and docs. Save the whole fitted pipeline (preprocessing + model) with joblib.
  • Options: load it inside the web app (once at start-up, not on every request); or wrap it as a separate web service behind a REST API, which is easier to upgrade and scale and can be called from any language; or use a cloud prediction service.
  • The book's cloud example is Google Cloud AI Platform: upload the joblib file to Cloud Storage and create a model version. Chapter 19 covers this for TensorFlow.

Monitor

  • Models "rot": the world changes, so performance can fall suddenly (a broken component) or slowly (data drift). A slow decline can go unnoticed for a long time.
  • Measure live performance through downstream metrics (e.g. sales from recommendations) or with human raters checking a sample, especially low-confidence cases. Raters can be experts, crowd workers, or the users themselves.
  • Also monitor the inputs: more missing values, mean or standard deviation drifting away from the training data, new categories. These warn you earlier than the output metrics.
  • Even a cats-vs-dogs model needs retraining eventually, because cameras, image formats and fashions change.

Maintain

  • Automate: collect and label fresh data, retrain and tune on a schedule, compare the new model with the old one on an updated test set, and deploy only if it isn't worse (if it is worse, investigate).
  • Keep backups of every model and every dataset version, and be able to roll back quickly.
  • Build test subsets for specific slices (the most recent data, inland vs. coastal districts…) to understand where the model is strong or weak.
  • Monitoring and infrastructure are often more work than building the model. The first project is slow; later ones are much faster.

Test yourself

Answer out loud first, then click the card.

The downstream team only uses "cheap / medium / expensive". What changes?
The task becomes classification, not regression. That's why you check assumptions before building anything.
Your errors include some huge outliers. RMSE or MAE?
MAE (ℓ1). RMSE (ℓ2) squares errors, so a few outliers dominate it. With bell-shaped errors, RMSE is fine.
Why split off the test set before exploring?
To avoid data snooping bias. Patterns you notice in the test data would shape your choices and make the final estimate too optimistic.
When does stratified sampling matter most?
When the dataset is small, or a key attribute has rare groups. A random split can then over- or under-represent those groups.
Why is OrdinalEncoder a poor choice for ocean_proximity?
The categories have no order, but the model would treat 0 and 1 as "closer" than 0 and 4. Use one-hot encoding.
A district's income is mistyped as 100. Which scaler suffers?
Min-max: every normal value is squeezed into a tiny range near 0. Standardisation is much less affected, and a robust scaler even less.
Training RMSE = 0, 10-fold CV RMSE is high. Diagnosis?
Severe overfitting (the book's decision tree). Constrain or regularise the model, get more data, or pick another model.
Grid vs randomized search: when do you pick randomized?
When the search space is large. It tries many values per hyperparameter, and n_iter fixes the compute budget.
