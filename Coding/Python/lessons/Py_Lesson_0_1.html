What Python is, and why it reads like English

Before you install anything or type a line, it's worth knowing what kind of thing Python actually is — and why its designers fought so hard to make it look almost like a sentence.

8 sections~12 minNo setup needed
1

Why this matters

You already know a language where the computer's comfort came first.

In C you tell the machine how many bytes to set aside, when to hand them back, and exactly what shape every value has. That precision buys you speed — it is why C runs the firmware in the robots on your line. But it means a program that simply reads a file and counts the words takes forty lines and three chances to leak memory.

Python made the opposite trade. It gives up some speed to buy back your time. The same word count is four lines, and none of them are about memory. Knowing which trade you are making — and when each one is right — is most of what this Part is for.

✨ Newly written

This framing is written for you specifically, because you're arriving at Python from C rather than from nothing. Most Python books assume the reader has never programmed. You have.

2

The mental model

C is compiled. You write source, a compiler translates the whole thing into machine code once, and you ship the result. The machine never sees your source again.

Python is interpreted. You write source, and a program called the interpreter reads it and acts on it, line by line, every time it runs. Your source is the program.

Two consequences fall straight out of that picture, and they explain almost every difference you'll meet later:

You can run a half-finished program. The interpreter only reaches line 40 when it gets there, so lines 1–39 run even if line 40 is nonsense. In C the compiler refuses the whole file.

Types are checked when the line runs, not before. Nobody asks what shape a value is until something actually tries to use it. That is why you never write int or char* in Python — and why a typo in a rarely-taken branch can sit undiscovered for months.

3

Walk-through — the same job, both languages

Count how many lines in a file mention the word "error". Here it is in Python, whole:

count_errors.py
# count the lines that mention "error"
count = 0
with open("log.txt") as f:
    for line in f:
        if "error" in line:
            count += 1
print(count)
line 3with open(...) as f — open the file and call it f. The with guarantees it gets closed, even if something goes wrong inside. This is Python's answer to the fopen/fclose pair you have to balance by hand in C. line 4for line in f — read it one line at a time. No counter, no length, no buffer. The file object knows how to hand out its own lines. line 5if "error" in line — read it out loud. That is the whole test. No strstr, no null check. line 6The indentation is the block. There are no braces; the four spaces are what puts this line inside the if, which is inside the for, which is inside the with.
✨ Newly written

Read lines 3–6 aloud as English: "with the open log file as f, for each line in f, if 'error' is in the line, add one to count." That sentence is nearly the code. This is the whole claim of the lesson title — and it is not an accident, it was a design goal.

→

All three. Notice what the Python versions share: no type declarations, no semicolons, no braces, no index variable. The distance between the sentence and the code is about as short as a programming language gets.
5

Predict the output

This file has a real mistake on the last line — widht is not a word. What happens when you run it?

area.py
width = 4
height = 3
print("starting")
print(width * height)
print(widht)
It prints, then crashes. starting and 12 appear on screen, and only then does Python reach line 5, fail to find anything called widht, and stop with NameError: name 'widht' is not defined.

This is the compiled/interpreted difference made concrete. A C compiler would have refused the whole file before printing anything. Python happily does four lines of correct work and then falls over — which is convenient when you're experimenting and dangerous in a script you leave running unattended.

6

What trips people here

🧱
Thinking "interpreted" means "slow, therefore bad"

Python is roughly 10–100× slower than C at raw loops — and almost none of your work will notice, because the heavy parts (NumPy, pandas) are themselves written in C. You write the English; the C runs underneath. Lesson 11.2 measures this properly.

␣
Treating indentation as decoration

Coming from C, whitespace is cosmetic and braces are structure. In Python the whitespace is the structure. Move a line four spaces left and you have changed which loop it belongs to. This is the single biggest adjustment for a C programmer.

🕰️
Expecting the error at the moment you write it

No compiler is watching. A misspelled name in an if branch that only runs on Sundays will be found on a Sunday. This is why Part V (Errors and Debugging) exists, and why tests matter more in Python than they do in C.

Your turn

Nothing to install yet — these are pen-and-paper, or a notes file.

Easy

Write, in plain English, what this does: for row in rows: if row["qty"] > 0: total += row["qty"]. One sentence, no jargon.

Medium

Take a small C program you've written — a loop that reads numbers and averages them will do. List every line whose only job is bookkeeping the machine needs (declaring types, tracking an index, freeing memory). Those lines are roughly what Python removes.

Stretch

The area.py example printed two correct lines before crashing. Name one real situation from your own work where that behaviour would be worse than refusing to start at all — and one where it would be better.

8

Quick recap

What to carry forward

  • Python is interpreted — your source is read and acted on line by line, every run. There is no separate executable.
  • That's why it runs until it fails rather than refusing to start, and why types are checked at the moment of use.
  • Indentation is structure, not style. Four spaces put a line inside a block; there are no braces.
  • The trade is machine time for your time. C for the firmware, Python for the analysis on top of it.
  • Speed worries are usually misplaced — the fast parts of Python are written in C already.
