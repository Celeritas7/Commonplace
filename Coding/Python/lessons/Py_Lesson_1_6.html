input(), type conversion, and the classic bug

input() always hands back a string. Always. Every beginner in every language meets the bug that follows, and in Python it has a particularly clear shape.

8 sections~11 minNo setup needed
1

Why this matters

One rule, and the whole lesson follows from it: input() returns a string.

Not a number when the user types a number. Not an integer when the prompt says “enter a number”. A string, every time, no matter what was typed.

C makes you say what you want up front — scanf("%d", &n) — and quietly does something strange when the input does not match. Python gives you text and makes converting it your explicit job. That is more honest, and it puts the error exactly where the bad data entered.

2

The mental model

Think of it as a boundary. Outside the program, everything is text. Inside, you want real types. Convert once, at the edge.

The converters are named after the types: int(), float(), str(), bool(). They are strict — int("abc") raises ValueError rather than guessing zero. That strictness is what makes the boundary useful: bad input fails immediately, at the point of entry, with a message naming the text that failed.

3

Walk-through

The pattern, and what each converter accepts.

age.py
raw = input("How many parts? ")   # always a string
count = int(raw)                     # convert at the boundary
print(f"double that is {count * 2}")

# the usual one-liner, once you trust the input
count = int(input("How many parts? "))
int("25")→ 25. Surrounding whitespace is fine: int(" 25 ") works. int("25.0")ValueError. int() parses integers only. Use int(float("25.0")) if you must accept both. float("3.5")→ 3.5. Also accepts "3", "1e6", "inf". int(3.9)→ 3. Converting a float truncates toward zero — it does not round. int(-3.9) is -3, not -4. Note this differs from //, from 1.2.

To survive a bad typist, wrap it — the full treatment is Part V, but the shape is worth seeing now:

safe.py
while True:
    try:
        count = int(input("How many parts? "))
        break
    except ValueError:
        print("Please type a whole number.")

Predict the output

The classic. The user types 5. What happens?

classic.py
n = input("Pick a number: ")
print(n * 3)
555. n is the string "5", and multiplying a string by an integer repeats it. "5" * 3 is "555".

What makes this the classic bug is that it does not crash. It produces a plausible-looking wrong answer, and in a longer program the nonsense surfaces far from here. Compare with n + 3, which does raise TypeError: can only concatenate str (not "int") to str — much kinder, because it fails immediately.

The fix is the habit from section 2: convert at the boundary. n = int(input(...)) and the whole class of problem is gone.

6

What trips people here

🔤
Forgetting that input() is always a string

Even when the prompt says “enter a number”. Even when they enter a number. Convert on the same line you read, and the rest of the program can trust the type.

🔢
int("3.0") raising ValueError

Surprising, but consistent: int() parses an integer literal, and "3.0" is not one. It has nothing to do with the value being whole. Use int(float(s)) when the text might have a decimal point.

✂️
Expecting int() to round

int(3.9) is 3 and int(-3.9) is -3 — it truncates toward zero. round(3.9) gives 4. And -7 // 2 gives -4. Three different roundings; pick deliberately.

8

Quick recap

What to carry forward

  • input() always returns a string — no matter what was typed.
  • Convert at the boundary: n = int(input(...)), once, where data enters.
  • "5" * 3 is "555", not 15 — the classic bug, and it doesn't crash.
  • int() is strict: int("3.0") raises. Use int(float(s)) for either form.
  • int(3.9) truncates toward zero; round() rounds; // floors.
  • Wrap conversion in try/except ValueError whenever a human is typing.
