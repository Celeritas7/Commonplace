Raising, custom exceptions, the hierarchy

Failing loudly at the moment something is wrong beats returning a sentinel value nobody checks. Raising is how you do that — and the hierarchy is why catching one name can catch several errors.

8 sections~11 minLinks to a live notebook
1

Why this matters

A function given bad input has three options: return a magic value, return None, or raise.

The magic value is the C tradition — return −1 and hope the caller checks. It never does, and −1 flows into an average as a real reading.

Returning None is better but still quiet: the failure surfaces later, in unrelated code, with a message about NoneType that says nothing about the cause.

Raising stops everything at the exact line where the problem was detected, with a message you wrote. The caller can catch it if it has something sensible to do; otherwise the traceback points straight at the cause. Failing early and loudly is almost always cheaper than failing late and quietly.

2

The mental model

Exceptions form a class hierarchy — a family tree — and catching a parent catches all its descendants.

Two practical consequences. except Exception: catches essentially every error your code can cause — but not KeyboardInterrupt, which sits under BaseException and is why the bare except: in 5.1 is dangerous. And except LookupError: catches both KeyError and IndexError, because both are children of it.

Walk-through

Raising built-ins, and defining your own.

raising.py
def set_quantity(part, qty):
    if not isinstance(qty, int):
        raise TypeError(f"qty must be an int, got {type(qty).__name__}")
    if qty < 0:
        raise ValueError(f"qty cannot be negative, got {qty}")
    part["qty"] = qty

# your own type, for errors specific to your program
class OutOfStockError(Exception):
    """Raised when an order exceeds available stock."""

def ship(part, n):
    if n > part["qty"]:
        raise OutOfStockError(f"asked {n}, have {part['qty']}")
    part["qty"] -= n

# callers can be specific about what they handle
try:
    ship(bolt, 100)
except OutOfStockError as e:
    print(f"cannot ship: {e}")

Predict the output

Which handler catches this, and why?

hierarchy.py
d = {"a": 1}

try:
    print(d["b"])
except LookupError:
    print("lookup failed")
except KeyError:
    print("no such key")
lookup failed. Except clauses are tested top to bottom, and the first one that matches wins — exactly like the elif chain in 2.1. KeyError is a subclass of LookupError, so the first clause matches and the second is never reached.

The except KeyError clause here is dead code. Python will not warn you about it.

The rule: order except clauses from most specific to most general. Put KeyError first and LookupError after it as a catch-all. Putting except Exception: first makes every clause below it unreachable.

6

What trips people here

📢
raise Exception("something went wrong")

Too generic to catch selectively — a caller wanting to handle just your error would have to catch everything. Pick a specific built-in, or define a subclass. It costs three lines.

🔇
Returning a sentinel instead of raising

return -1 or return None for a genuine failure pushes the problem to a caller who probably will not check. Raise at the point of detection; that is where the useful context is.

🪆
Except clauses in the wrong order

General before specific makes the specific ones unreachable, silently. Narrowest first, always.

8

Quick recap

What to carry forward

  • Raise at the point of detection — a loud failure beats a sentinel value nobody checks.
  • Pick the fitting built-in: ValueError (right type, wrong value), TypeError (wrong type), KeyError/IndexError (not found).
  • Put the offending value in the message. It ends the investigation instead of starting one.
  • A custom exception is class MyError(Exception): and a docstring. Three lines.
  • Exceptions form a hierarchy — catching a parent catches its children.
  • Order except clauses narrowest first, or the later ones become unreachable dead code.
