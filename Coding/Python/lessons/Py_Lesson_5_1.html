try / except / else / finally

C returns an error code you can ignore. Python raises an exception you cannot. Catching it well means catching narrowly — and the four clauses each have a job worth knowing.

8 sections~12 minLinks to a live notebook
1

Why this matters

In C, fopen returns NULL on failure and nothing forces you to look. Skip the check and the program continues with a null pointer until it crashes somewhere unrelated.

Python's equivalent raises. If you do not handle it, the program stops right there with a traceback naming the file and the line — the report you learned to read in 0.4. You cannot accidentally continue with a broken value, because there is no value to continue with.

So the question is never “did it work?” but “which failures do I want to handle here, and which should stop the program?” That second half matters as much as the first.

2

The mental model

Four clauses. Most code uses two.

clauses.py
try:
    value = int(raw)          # code that might fail
except ValueError:
    print("not a number")      # runs only on THAT failure
else:
    print(f"got {value}")      # runs only if NOTHING failed
finally:
    print("done")             # runs either way, always
ClauseRuns whenUse for
tryalways — it is the guarded blockkeep it small; only the risky line
exceptthat specific exception was raisedhandling a failure you expected
elsethe try finished with no exceptionwork that should not itself be guarded
finallyalways, even on return or re-raisecleanup — closing, releasing, restoring

The else is the one people skip, and it earns its place: code in else is not covered by the except. Put the risky call in try and everything that follows in else, and you cannot accidentally catch a ValueError raised by the success path.

Walk-through

Catching narrowly, and catching more than one.

catching.py
# one specific exception
try:
    qty = int(input("Quantity: "))
except ValueError:
    qty = 0

# several, same handling
try:
    data = load(path)
except (FileNotFoundError, PermissionError):
    data = {}

# several, different handling — and keeping the object
try:
    result = a / b
except ZeroDivisionError:
    print("b was zero")
except TypeError as e:
    print(f"wrong types: {e}")   # e is the exception object

# cleanup that must happen whatever occurs
f = open(path)
try:
    process(f)
finally:
    f.close()                     # even if process() raises

Predict the output

A function with both return and finally. What does it print?

finally.py
def check():
    try:
        return "from try"
    finally:
        print("cleanup")

print(check())
cleanup, then from try. The return value is computed and set aside, then finally runs, and only then does the function actually return.

That ordering is the whole guarantee of finally: it runs on the way out, no matter how you leave — normal completion, return, break, or an exception propagating upward. There is no path that skips it.

Which is exactly why it is the right place for closing a file, releasing a lock, or restoring a setting. And why a return inside finally is a bad idea — it would silently discard whatever the try was returning, and swallow any exception on its way past.

6

What trips people here

🕳️
except: with nothing after it

A bare except catches everything — including KeyboardInterrupt when you press Ctrl-C, and SystemExit. A loop with a bare except can become genuinely unstoppable. If you must be broad, use except Exception:, which leaves those two alone.

🤐
Catching and doing nothing

except ValueError: pass makes the failure invisible. Later, when something is wrong, there is no trace of where it started. At minimum log it. Silent handlers are how a bug survives for months.

🥅
Wrapping too much in one try

A twenty-line try with one except ValueError will catch a ValueError from anywhere in those twenty lines, including places you never considered. Guard the single risky call; put the rest in else.

8

Quick recap

What to carry forward

  • An unhandled exception stops the program with a traceback — you cannot ignore it the way you can a C return code.
  • Catch narrowly. Name the exception you expect; let the others through.
  • except X as e: binds the object — str(e) is the detail line.
  • else runs when nothing failed, and is not covered by the except. finally always runs, even on return.
  • Keep the try block small — one risky call, not twenty lines.
  • Never write a bare except: — it swallows Ctrl-C. Use except Exception:.
