Truthiness, membership, and the ternary

Empty things are false. That single rule replaces a pile of length checks and null tests — and creates exactly one trap, which is worth meeting on purpose.

8 sections~11 minLinks to a live notebook
1

Why this matters

In C, testing whether a string has content means if (s != NULL && s[0] != '\0').

In Python it is if s:.

That works because Python asks every object whether it considers itself true, and the built-in types all answer the same sensible way: empty is false, non-empty is true. One rule covers strings, lists, dicts, sets and tuples, and it removes most of the ceremony from the conditions you write.

2

The mental model

Everything is true except a short list. Learn the list, and you know the rule.

FalsyType
Falseboolthe obvious one
NoneNoneType“no value” — Python's null
0   0.0int, floatzero of any numeric type
""strempty string
[]   ()   {}list, tuple, dict, setempty containers

Everything else is truthy — including "0", "False", [0] and -1. A string containing the character zero is a non-empty string, so it is true. That catches people once.

Membership follows the same instinct for readability. in works on everything: "a" in word, 3 in numbers, "name" in record. On a dict it tests the keys.

The ternary puts a small choice on one line, written in reading order rather than C's ?::

label = "ok" if count > 0 else "empty"   # C: count > 0 ? "ok" : "empty"
3

Walk-through

What the rule buys you in practice.

truthy.py
items = []

# the C-shaped way — works, but nobody writes this
if len(items) > 0:
    print("has items")

# the Python way
if items:
    print("has items")
else:
    print("empty")

# membership reads like English
record = {"name": "Aniket", "city": "Tokyo"}
if "name" in record:          # checks KEYS, not values
    print(record["name"])

# ternary, in reading order
status = "active" if items else "idle"
if items:Reads as “if there are items”. Shorter, and it works unchanged if items later becomes a string or a dict. in on a dictTests keys. To test values, "Tokyo" in record.values(). Forgetting this is a common source of quietly-false conditions. ternaryUse it when the whole thing fits comfortably on one line. If you find yourself nesting ternaries, write the if block out — nested ones are genuinely hard to read.

5

Predict the output

A sensor reads zero — a perfectly valid measurement. What prints?

trap.py
reading = 0

if reading:
    print("got a reading")
else:
    print("no reading")
no reading — and this is the one place truthiness will hurt you.

Zero is falsy, so “the sensor returned 0” is indistinguishable from “the sensor returned nothing”. Same for an empty string that a user legitimately typed, and for an empty list that is a valid result.

The fix is to test for the thing you actually mean:

if reading is not None:

Rule of thumb: when 0, "" or [] are legitimate values in your data, test against None explicitly. When “empty” and “missing” genuinely mean the same thing, plain truthiness is right and shorter.

6

What trips people here

0️⃣
Treating 0 and None as interchangeable

They are both falsy but they mean different things: 0 is a measured value, None is the absence of one. Once your data can contain a real zero, if x: is a bug waiting for the right input.

🧾
if x == True:

Redundant, and subtly wrong — 1 == True is True but 2 == True is False, so if x == True rejects truthy values that if x accepts. Just write if x:.

🔑
Assuming in on a dict searches values

"Tokyo" in record is False even when a value is "Tokyo" — it looked at the keys. Use .values() or .items() when you mean the other thing. Covered fully in 3.4.

8

Quick recap

What to carry forward

  • Empty is false. "", [], {}, (), 0, 0.0, None, False — everything else is true.
  • Write if items:, not if len(items) > 0:.
  • "0" and "False" are non-empty strings, so they are true.
  • in on a dict tests keys.
  • The trap: 0 is falsy. When zero is a legitimate value, test is not None.
  • Ternary reads in order: a if cond else b. Don't nest them.
