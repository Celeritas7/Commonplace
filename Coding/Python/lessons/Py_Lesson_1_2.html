Numbers and arithmetic; //, %, **

Python integers never overflow, division always gives a float, and 0.1 + 0.2 is not 0.3. Two of those will delight you and one will eventually cost you an afternoon.

8 sections~12 minNo setup needed
1

Why this matters

In C you choose a numeric type and live with its edges: int overflows around two billion, / truncates when both sides are integers, and you cast to control it.

Python removes two of those problems and keeps the third. Integers grow to whatever size fits in memory — 2 ** 1000 is an ordinary expression with an exact answer. Division always produces a float, so 7 / 2 is 3.5, never 3.

What Python does not fix is floating point. 0.1 + 0.2 is not 0.3, here or in C or anywhere else, and knowing why keeps you out of a trap that appears the first time you compare two computed prices.

2

The mental model

Three numeric types, and you will use two of them.

TypeWhat it isEdge to know
intWhole numbers, unboundedNo overflow, ever. Big ones just get slower.
floatDecimals — 64-bit, same as C's doubleApproximate. About 15–17 significant digits.
DecimalExact decimal arithmetic, from the stdlibSlower. Use it for money.

And two divisions, which is the thing to fix in your fingers:

/ true division

Always returns a float. 6 / 3 is 2.0, not 2. Even when it divides evenly.

// floor division

Divides and rounds down. 7 // 2 is 3. This is closest to C's integer /, but not identical — see the mistakes.

📖 From your notes

Your 2_Module_Math.py script already covers math.floor, math.ceil and math.sqrt. Those are the same operations reached a different way — a // b is math.floor(a / b), and for large numbers the operator is both faster and exact where the float route is not.

Predict the output

A price calculation. What prints?

money.py
total = 0.1 + 0.2
print(total)
print(total == 0.3)
0.30000000000000004, then False. Neither 0.1 nor 0.2 can be written exactly in binary, any more than ⅓ can be written exactly in decimal. The tiny errors add up and show.

This is not a Python flaw — C, Java and your calculator app all do it. What matters is the habit it forces: never compare floats with ==. Compare within a tolerance:

math.isclose(total, 0.3)  →  True

And for money specifically, use Decimal("0.1") from the decimal module, which is exact because it works in base 10. Slower, but a rounding error in a total is not a trade you want.

6

What trips people here

➗
Using / where you meant //

mid = len(items) / 2 gives a float, and items[mid] then raises TypeError: list indices must be integers or slices, not float. In C the same line would have silently truncated. Python refuses instead — which is safer, but only if you recognise the message.

➖
Assuming // and % behave like C on negatives

C truncates toward zero: -7 / 2 is -3. Python floors: -7 // 2 is -4. And -7 % 2 is 1 in Python but -1 in C. Python's rule is that the remainder takes the sign of the divisor. If you are porting arithmetic from C, check every negative case.

💸
Using floats for money

Add ten prices and compare to an expected total and it will eventually fail by a fraction of a cent. Either work in integer minor units — store 1250 rather than 12.50 — or use decimal.Decimal. Pick one before the first bug, not after.

Quick recap

What to carry forward

  • Python ints never overflow. 2 ** 1000 is exact and ordinary.
  • / always returns a float. // floors to an int. Index with //.
  • % is remainder, ** is power — no pow() needed.
  • On negatives Python floors where C truncates: -7 // 2 is -4, not -3.
  • Never compare floats with ==. Use math.isclose().
  • For money use integer minor units or decimal.Decimal, decided up front.
