Strings — creation, indexing, slicing

A Python string is a sequence you can index, slice and loop over — and one you can never change. Both halves of that matter, and the slicing notation you learn here reappears on every list in Part III.

8 sections~12 minLinks to a live notebook
1

Why this matters

In C a string is an array of char ending in a zero byte, and half the work is remembering that.

Python has no character type at all — a single character is just a string of length one. There is no terminator, no buffer to size, no strlen walking the array to count. len(s) is instant because the string knows its own length.

What you get instead is a sequence: something you can index, slice, loop over and test membership in. Learn the notation here and it transfers unchanged to lists, tuples and ranges later.

2

The mental model

Every position has two numbers: one counting forward from 0, one counting backward from −1.

Slicing is written s[start:stop] and the rule that makes everything else consistent is: start is included, stop is excluded. So s[0:3] is "PYT" — three characters, positions 0, 1 and 2.

That looks arbitrary until you notice two things fall out of it for free. s[:n] and s[n:] split the string with no overlap and nothing lost. And len(s[a:b]) is just b - a. Both are wrong under any other convention.

The second fact about strings: they cannot be changed. s[0] = "J" is an error. Every operation that looks like it edits a string actually builds a new one.

Predict the output

One of these two lines raises an error. Which, and why?

edges.py
s = "PYTHON"       # length 6
print(s[10])
print(s[2:10])
Indexing is strict; slicing is forgiving. s[10] asks for a character that does not exist, so Python raises IndexError: string index out of range. s[2:10] asks for a range, and Python gives you the overlap with what exists — 'THON', no error.

That asymmetry is deliberate and useful: s[:200] is a safe way to take “up to the first 200 characters” without checking the length first. But it also means a slice bug stays silent. If a slice returns an empty string when you expected content, check your indices — nothing will have complained.

6

What trips people here

🔒
Trying to change a character in place

s[0] = "J" raises TypeError: 'str' object does not support item assignment. Strings are immutable. Build a new one instead: "J" + s[1:]. Coming from C, where a string is a writable array, this is the biggest adjustment.

🔁
Building a long string by repeated += in a loop

Every += creates a whole new string and throws the old one away. For a few dozen pieces it does not matter; for tens of thousands it becomes quadratic and slow. Collect the pieces in a list and "".join(parts) at the end — covered in 1.4.

↔️
Forgetting that stop is excluded

s[0:len(s)] is the whole string, not one short — but s[0:len(s)-1] silently drops the last character. When you catch yourself writing -1 inside a slice, check whether you actually wanted it.

8

Quick recap

What to carry forward

  • No char type, no terminator — a single character is a string of length 1.
  • Two rulers: 0..n-1 forward and -1..-n backward. s[-1] is the last item.
  • s[start:stop:step] — start included, stop excluded. That is why s[:n] + s[n:] is the whole string.
  • Indexing is strict, slicing is forgiving. s[10] raises; s[2:10] just clamps.
  • s[::-1] reverses. "ab" in s tests for a substring.
  • Strings are immutable — every “edit” builds a new string.
