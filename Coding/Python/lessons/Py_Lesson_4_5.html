Scope — local, global, and constants

Where a name lives, who can see it, and why assigning inside a function behaves differently from reading. The rule is short; the one surprise is worth meeting deliberately.

8 sections~11 minNo setup needed
1

Why this matters

C has file scope and block scope, decided by where the braces are. Python has function scope, decided by where the def is.

A name created inside a function belongs to that call and disappears when it returns. Two calls to the same function have entirely separate copies. That much is familiar.

The part that surprises people is the asymmetry: reading a global name from inside a function works; assigning to one does not. Understanding why takes two minutes and prevents a genuinely confusing error.

2

The mental model

Python looks names up in four places, in a fixed order — LEGB.

ScopeWhereExample
LocalInside the current functiona parameter, or a name assigned in the body
EnclosingAn outer function wrapping this onenested functions — 4.6
GlobalTop level of the filemodule-level names and constants
Built-inAlways availableprint, len, sum, range

The first match wins, which is exactly why 1.1 warned against naming a variable list — a local or global list is found before the built-in one, and the built-in becomes unreachable.

legb.py
RATE = 0.08              # global — capitals signal "constant"

def total(amount):
    tax = amount * RATE    # tax is LOCAL; RATE read from GLOBAL
    return amount + tax

print(total(100))
# print(tax)   → NameError: tax does not exist out here
3

Walk-through

Reading is free. Assigning changes everything.

assign.py
count = 0

def show():
    print(count)        # fine — reads the global

def bump():
    count = count + 1   # UnboundLocalError

def bump_ok():
    global count        # explicit: I mean the global one
    count = count + 1

Why does bump fail? Because Python decides a name's scope by scanning the whole function body before running it. It sees count = ... somewhere in bump, concludes count is local to bump, and then the right-hand side tries to read a local that has not been assigned yet.

So the rule is: if a name is assigned anywhere in a function, it is local everywhere in that function — including on lines above the assignment.

✨ Newly written

The error message names it precisely: UnboundLocalError: cannot access local variable 'count' where it is not associated with a value. That phrase “local variable” is the clue — Python is telling you it decided the name was local, which is usually the surprise.

5

Predict the output

What happens when bump() is called?

unbound.py
count = 10

def bump():
    print(count)
    count = count + 1

bump()
UnboundLocalError on the print line — before anything is printed at all.

This is the part that surprises. Python scanned the whole body of bump before running a single line, found the assignment count = count + 1, and marked count as local for the entire function. So by the time print(count) runs, it is looking for a local count that has no value yet. The global 10 is never consulted.

Delete the assignment line and the print works fine. The assignment on line 5 changes the meaning of line 4 — which is unusual, and worth remembering as the signature of this error.

6

What trips people here

🌍
Reaching for global to fix an UnboundLocalError

It silences the error, and it makes the function's behaviour depend on hidden state. Prefer passing the value in and returning the new one — the function then does the same thing every time it is called with the same arguments, which is what makes it testable.

🏷️
Assuming UPPER_CASE is enforced

It is a convention, nothing more. Python will happily let you reassign RATE. The capitals tell a human not to; they tell the interpreter nothing.

🔁
Expecting a loop variable to be scoped to the loop

In C, for (int i = ...) confines i to the loop. In Python the loop variable survives afterwards, holding the last value — and if the loop never ran, the name may not exist at all.

8

Quick recap

What to carry forward

  • Names resolve Local → Enclosing → Global → Built-in. First match wins.
  • A name assigned inside a function is local to the whole function, even above the assignment line.
  • Reading a global works; assigning to one needs the global keyword.
  • UnboundLocalError means Python decided the name was local — look for an assignment further down.
  • Prefer parameters in, values out over global. Testable beats convenient.
  • UPPER_CASE is a message to readers, not a rule Python enforces.
