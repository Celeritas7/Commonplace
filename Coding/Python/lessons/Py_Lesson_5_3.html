The six-step debugging routine

Debugging is not a talent. It is a procedure, and you already wrote it down once. This lesson makes it explicit, because the difference between five minutes and an afternoon is almost always whether you followed it.

8 sections~12 minFrom your own notes
1

Why this matters

Everyone debugs by instinct at first: stare at the code, change something plausible, run it again, repeat.

It works on small bugs and collapses on real ones, because it has no memory and no stopping condition. You cannot tell whether you are making progress, and you frequently introduce a second bug while hunting the first.

The alternative is a routine. You already have one — the beginner practice notebook lists exactly these steps — and it is worth stating properly because the steps are in a specific order for a reason.

Six steps. Each one narrows where the bug can be hiding.

3

Walk-through

The two steps people skip, and why they are the load-bearing ones.

Step 1, describe. Write one sentence: “I expected the total to be 15, and it printed 10.” A surprising number of bugs are solved by this alone, because stating the expectation exposes that the expectation was wrong. It also gives you a test for when you are done.

Step 3, play computer. Take the smallest failing input and walk the code by hand, on paper, writing down every variable after every line. No running it. This is slow and it is the step that actually finds the bug, because it forces you to read what the code says rather than what you meant.

trace.py
def total_to(n):
    total = 0
    for i in range(n):
        total += i
    return total

print(total_to(5))      # expected 15, got 10
trace itn=5. range(5) yields 0,1,2,3,4. total goes 0 → 0 → 1 → 3 → 6 → 10. Return 10. the findingThe trace shows 5 was never added. range(5) stops at 4 — the excluded stop from 2.3. the fixrange(1, n + 1). Found by tracing in thirty seconds, not by staring. why it worksHand-tracing makes you evaluate range(5) for real instead of reading it as “up to five”.

And step 5, print — but deliberately. Not scattered print(x) calls, but labelled ones at the boundaries between stages, using the = form from 1.5:

print(f"{raw = }")              # raw = '  25 '
print(f"{parsed = } {type(parsed) = }")   # the value AND its type

5

Predict the output

You add a print to check a value. What is wrong with this?

printing.py
def clean(rows):
    for r in rows:
        print(r)
        r["qty"] = int(r["qty"])
    return rows
It prints the input, not the thing that fails. If int(r["qty"]) raises, you see the row — but you already knew the row. What you need is which field, and what it actually contained.

Better:

print(f"{r['qty'] = } {type(r['qty']) = }")

Two rules for print debugging. Print the value and its type — half of Python bugs are a string where a number was expected, and 25 and "25" print identically. And print immediately before the failing line, not at the top of the loop.

Then delete them when you are done. Leftover debug prints are how a script ends up with mystery output nobody dares remove.

6

What trips people here

🎲
Changing things at random

If you cannot say why a change should fix it, you are not debugging — you are shuffling. And when it appears to work you will not know whether you fixed it or hid it.

🔧
Fixing more than one thing at a time

Change one thing, run, observe. Two changes and a passing test tells you nothing about which mattered — or whether they cancelled out.

🙈
Not reading the error because it is long

The traceback frames between the top and bottom are the call path, and they are usually what you need. 0.4 covers reading them; the mistake is not reading them at all.

8

Quick recap

What to carry forward

  • Debugging is a procedure, not a talent. The order matters.
  • 1 Describe — expected versus actual, in one sentence. Solves a surprising number outright.
  • 2 Reproduce — smallest input that fails every time.
  • 3 Play computer — hand-trace on paper. This is the step that finds it, and the one people skip.
  • 4 Read the error in full, bottom-up. 5 Print value and type, right before the failing line. 6 Debugger last.
  • One change at a time, and only changes you can justify.
